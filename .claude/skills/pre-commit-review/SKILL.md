# Передкомітна перевірка

Мета — перед комітом знайти проблеми, які інакше знайде рев'юер або користувач, і
нічого не «виправити» всліпу: деякі відхилення від норм є **вимогою макету** (Figma).

## Правила поведінки (головне)

1. **Механічне — виправляй і звітуй:** помилки типів, помилки lint, форматування
   prettier, невикористані імпорти/змінні, сміттєві файли, забуті `console.log`.
2. **Семантика, функціонал, доступність, відхилення від CLAUDE.md чи скілів — СПОЧАТКУ
   ПИТАЙ.** Не правити, доки користувачка не відповіла: те, що виглядає помилкою, може
   бути вимогою макету. Формулюй питання так: що знайшла → чому це відхилення → який
   варіант пропонуєш → що втратимо.
3. **Коміт — лише після явної згоди.** Пуш — лише коли просять. Ніколи `--no-verify`,
   ніколи `git add -A` навмання. `PLAN.md` не комітиться.
4. **Українською** — кожну дію і кожен запит дозволу коротко коментуй українською;
   підсумок — стислий.
5. Не читай `.env*` і не витягуй з нього секрети (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`).

## Крок 0 — контекст

- `git status --short`, `git branch --show-current`, `git fetch`.
- Що змінилось у гілці: `git diff --stat origin/dev...HEAD` + незакомічене (`git diff HEAD`).
- Прочитати змінені файли **повністю** (не лише diff): помилки часто в сусідніх рядках.
- Untracked-файли: чи всі потрібні, чи немає сміття (скріншоти, scratch, `*.log`).

## Крок 1 — автоматичні перевірки

| Що | Команда | Примітки |
|---|---|---|
| Типи | `npm run typecheck` | |
| Lint | `npm run lint` | |
| Форматування | `npx prettier --check <змінені файли>` | лише змінені |
| Build | `npm run build` | **обов'язково при кожній передкомітній перевірці** — без успішного білду коміту немає |

Build — блокер: якщо `npm run build` падає, коміт не робимо, доки білд не пройде. Успіх =
`Compiled successfully` + `Finished TypeScript` + список маршрутів без помилок.

**Build на Windows:** спершу зупинити `next dev` (паралельний `next build` ламає `.next`
dev-сервера), після — `rm -rf .next` перед повторним стартом dev. Підняти dev назад лише
якщо він був запущений.

## Крок 2 — ревʼю коду (читанням)

Пройти по змінених файлах за чекліст. Кожна знахідка → у звіт із `файл:рядок`.

**Маніфест (CLAUDE.md) і KISS/YAGNI / overcoding**
- Нічого «на майбутнє»: зайві абстракції, шари, обгортки, пропси, які ніхто не передає.
- Жодного `any`; тип локалі — `AppLocale` з `src/i18n/routing.ts`, не `'ua' | 'en'` руками.
- Server Components за замовчуванням; `'use client'` лише найнижче з інтерактивом.
- Ніяких `useEffect`+`useState` для даних, перекладів, URL, детекції браузера.
- `Link`/`useRouter` з `@/i18n/navigation`, не з `next/link` і не `window.location`.

**Перевикористання** (скіл `reuse-before-build`)
- Чи немає вже такого компонента в `src/components/ui`, `src/components`, хука в
  `src/hooks`, хелпера в `src/utils`? Модалки — лише через наявні модальні компоненти,
  блокування скролу — лише `useScrollLockV2`.
- Токени з `src/styles/globals.css` замість сирих hex (скіл `tailwind-token-naming`).
- Один джерельний компонент для десктоп/мобілки (`responsive-shell-single-source`).

**i18n**
- Кожен новий рядок UI — у **обох** `public/locales/ua.json` і `en.json`, ключі однакові.
- Немає захардкодженого тексту в JSX (типу «Go to Home»).
- Дати/числа — через `useFormatter`/`getFormatter` з next-intl (таймзона з `src/i18n/request.ts`),
  не через `new Date().toLocale…`/`date-fns format` у компонентах, що рендеряться на клієнті.

**Розмітка й семантика** (скіл `structure-and-element-anti-patterns`)
- Заголовки по порядку (один H1 на сторінці), лендмарки (`main`, `nav`, `header`, `footer`),
  списки — `ul/li`, кнопки — `<button type="button">`, навігація — `<Link>`.
- Немає вкладених інтерактивних елементів, `div` всередині `button`, `div onClick`,
  `key={index}`, фіксованих px-висот секцій замість гнучкої розкладки, зайвих обгорток.

**Атрибути**
- Зображення: `next/image`, осмислений `alt` (декор — `alt=""`), `sizes`, `priority`
  лише на LCP (скіл `nextjs-image-weight`).
- Поля форми: видимий `label`, `type`, `autocomplete`, помилка через `aria-describedby`.
- Зовнішні посилання: `rel="noopener noreferrer"` при `target="_blank"`.

**Доступність**
- Усе керується з клавіатури; видимий фокус, що **не змінює геометрію**
  (`ui-focus-no-layout-shift`); без додатного `tabIndex`; модалки: `role="dialog"`,
  `aria-modal`, підпис, Esc, фокус. Відхилення за макетом — **питати**.

**SEO** (скіл `seo-skill`)
- Нова сторінка має `generateMetadata` з перекладеними `title`/`description` і
  `alternates`; невідомий slug → `notFound()`, не `return null`; маршрут у `sitemap.ts`.

**Безпека** (скіли `input-bounds-and-ownership`, `external-call-safety`)
- Route handler валідує тіло на сервері, обмежує довжину полів, має таймаут на зовнішній
  виклик і не віддає клієнту тіло помилки від Telegram.

**Сміття й тимчасове:** `console.log`, закоментований код, тестові дані в `src/data`,
тимчасові заглушки — не видаляти мовчки, а **спитати**.

## Крок 3 — стійкість до відсутніх даних

- Сторінки зі slug: невідомий slug → 404 (перевірити `curl -o /dev/null -w "%{http_code}"`).
- Порожній масив новин/кейсів не ламає слайдер.
- Помилки на клієнті `curl` не ловить — попросити глянути консоль (hydration warnings).

## Крок 4 — звіт

Стислий список за пріоритетом: **Блокери → Потребує рішення → Дрібниці → Виправлено**.
Кожен пункт: `файл:рядок` — що — чому — пропозиція. Після відповідей виправити тільки
погоджене й повторити Крок 1 для зачепленого.

## Крок 5 — синхронізація з dev (обов'язково перед фінальним комітом)

Гілка береться з `dev` і мерджиться в `dev` через ПР. Пуш у `dev` запускає деплой на
dev-сервер (`.github/workflows/ci.yml`) — тому ніяких прямих пушів у `dev`.

1. `git fetch origin`; є нові коміти в `origin/dev`? (`git log HEAD..origin/dev --oneline`).
2. Якщо є — сухий прогін конфліктів: `git merge-tree --write-tree HEAD origin/dev`.
   Сказати користувачці, що чіпає merge.
3. Змерджити `origin/dev` у гілку — лише з її згоди. Конфлікти вирішувати **бережно**.
4. Після merge: якщо змінився `package-lock.json` — `npm ci`; повторити typecheck + lint + build.
5. Лише тепер — коміт.

## Крок 6 — коміт

- Показати, що саме входить (`git status`), додавати файли **поіменно**.
- Повідомлення стисле, англійською, про «навіщо».
- Пуш — окремо, тільки на прохання. Текст ПР у ` ```markdown ` блоці, **українською**:
  «Що зроблено», «На що звернути увагу», «Перевірка».

## Підсумок для користувачки

Що перевірено, що виправлено, що чекає її рішення, чи змерджено dev, і чи можна комітити.
